# The Process Model

---

## Every Program Is a Process

When you run a command, the kernel creates a **process**:

<v-clicks>

- Unique **PID** (process ID) and **PPID** (parent PID)
- Open **file descriptor** table — stdin, stdout, stderr, and more
- **Virtual address space** — private memory mapping
- **Signal disposition** — what to do when a signal arrives
- **Namespace memberships** — which system resources it can see

</v-clicks>

<!--
Emphasize: namespaces are the key. Containers are processes with different namespace memberships.
This is not a metaphor — a container process is structurally identical to any other process.
-->

## Exploring `/proc`

The kernel exposes live process state as files in `/proc/<PID>/`.
No special tools required — just `cat` and `ls`.

- `fd/` — open file descriptors
- `maps` — virtual memory regions
- `status` — human-readable process info
- `net/` — network state visible to this process

::right::

```bash {1-2|4-5|7-8|10-11}
# Your shell's PID
echo $$

# Open file descriptors
ls -la /proc/$$/fd

# Memory regions
cat /proc/$$/maps | head -5

# Network interfaces visible to this process
cat /proc/$$/net/if_inet6
```

<!--
Live demo: run these in the terminal. Show that /proc/1/maps requires root.
That's foreshadowing for container security — root in the container, restricted on the host.
-->

## Objectives

1. Map running processes using `ps` and `pstree`
2. Inspect a process's open files and memory via `/proc`
3. Send signals and observe process behavior

## Steps

```bash
# All processes, full detail
ps auxf

# Visual tree
pstree -p

# Find sshd's PID
PID=$(pgrep -x sshd | head -1)

# Inspect its open file descriptors
ls -la /proc/$PID/fd

# Inspect its command line
cat /proc/$PID/cmdline | tr '\0' ' '

# Send SIGHUP to reload (safe for sshd)
sudo kill -HUP $PID
```

# File System Hierarchy

---

## The FHS at a Glance

<div class="grid grid-cols-2 gap-6">
<div>

**System configuration**
- `/etc` — static config files
- `/var` — variable data: logs, spools, caches
- `/run` — runtime state (cleared on boot)

**Programs**
- `/usr/bin`, `/usr/sbin` — user and admin commands
- `/usr/lib` — shared libraries

</div>
<div>

**Kernel interfaces**
- `/proc` — process and kernel state
- `/sys` — device and driver state
- `/dev` — device nodes

**Ephemeral**
- `/tmp` — temporary files (often tmpfs)
- `/mnt`, `/media` — mount points

</div>
</div>

<!--
Key for container work: /proc and /sys are virtual — they're generated by the kernel.
In a container, the container sees its own /proc but shares the host /sys.
-->

## Permissions and Ownership

Every file has an owner, group, and permission bits.
The kernel enforces these on every `open()` call.

- `r` (4) — read the file / list the directory
- `w` (2) — write the file / create/delete in directory
- `x` (1) — execute the file / enter the directory

::right::

```bash {1|3-4|6-7|9-10}
# Show ownership and mode
ls -la /etc/passwd

# Change owner (root only)
chown user:group file

# Change permissions (symbolic)
chmod u+x,go-w script.sh

# Numeric mode: rwxr-xr-x
chmod 755 script.sh
```

<!--
Note: directory x-bit is often misunderstood. You need x to cd into a dir or access files inside it,
even if you know the filename. This matters in container image builds.
-->

# systemd

---

## Unit Types You'll Use Daily

<v-clicks>

- **service** — a long-running daemon (nginx, sshd, kubelet)
- **socket** — socket-activated service (starts on first connection)
- **timer** — cron replacement with calendar expressions
- **target** — grouping of units, like a runlevel milestone
- **mount** — declarative filesystem mounts (`/etc/fstab` is still supported)

</v-clicks>

<!--
In Kubernetes, systemd manages the node-level services: kubelet, crio/containerd.
Understanding systemd is essential for debugging node issues.
-->

## Day-to-Day systemd Commands

The `systemctl` and `journalctl` pair covers 90% of service management tasks.

::right::

```bash {1-4|6-8|10-12|14-16}
# Service lifecycle
systemctl start nginx
systemctl stop nginx
systemctl restart nginx

# Enable/disable on boot
systemctl enable nginx
systemctl disable nginx

# Check status
systemctl status nginx
systemctl is-active nginx

# Follow logs (like tail -f)
journalctl -u nginx -f
journalctl -u nginx --since "1 hour ago"
```

<!--
Show journalctl -xe for debugging a failed service — it's the first thing to run.
-->

heading: "Write and Manage a systemd Service"
duration: "20 min"

## Objectives

1. Write a minimal shell script that loops and logs output
2. Create a `.service` unit file for it
3. Enable, start, and monitor it with `journalctl`

## Steps

```bash
# Create the service script
sudo tee /usr/local/bin/workshop-logger.sh > /dev/null <<'EOF'
#!/bin/bash
while true; do
  echo "Workshop logger running at $(date)"
  sleep 5
done
EOF
sudo chmod +x /usr/local/bin/workshop-logger.sh

# Create the unit file
sudo tee /etc/systemd/system/workshop-logger.service > /dev/null <<'EOF'
[Unit]
Description=Workshop Logger Service
After=network.target

[Service]
ExecStart=/usr/local/bin/workshop-logger.sh
Restart=on-failure

[Install]
WantedBy=multi-user.target
EOF

# Reload systemd and start
sudo systemctl daemon-reload
sudo systemctl enable --now workshop-logger

# Watch the logs
journalctl -u workshop-logger -f
```

<!--
FACILITATOR NOTE:
- Expected: service starts, logs appear in journalctl every 5 seconds
- Common issue: ExecStart path wrong — check with `systemctl status workshop-logger`
- Ask: "What happens if the script crashes?" — Restart=on-failure triggers restart
- Clean up: systemctl disable --now workshop-logger && rm the files
-->

## Chapter 1 Summary

<v-clicks>

- Linux processes are isolated by PID, file descriptors, and virtual memory
- `/proc` exposes live kernel state — no special tools needed
- The FHS organizes the filesystem; `/proc` and `/sys` are virtual kernel interfaces
- systemd manages the full service lifecycle: start, stop, enable, log

</v-clicks>
